# Synapse Architecture & Coding Standards

## System Invariants & Authoritative Boundaries
- System Principle: Core decides, Maestro delivers.
- Authority Model: CLAUDE.md is the immutable constitution. Do not alter architecture, add NLP/prose generation inside Core, or introduce probabilistic logic on your own initiative.
- Pipeline Boundaries: Constitutional Airlock (Ingestion) -> Constitutional Adjudication Engine (Core) -> Evidence Emitter (Audit).
- Fail-Closed Doctrine: Reject unstructured prose or invalid schemas immediately with HTTP 422 / Schema Error. Zero internal NLP/prose parsing inside Core.
- Core Adjudication Constraints: Stateless, pure functions, zero-generation logic executing deterministic rule checks.

## Locked Design Principles
- Supervisor UI Principle: No GO/NO-GO surface may present a standalone verdict. Every decision shown to a user must be paired with the Rule ID and the full set of evaluated sub-conditions (pass/fail per condition); for NO-GO, the specific conflicting condition must be shown explicitly. Applies to every delivery surface (dashboard, WhatsApp, Telegram, future channels).
- Hybrid Surface Design: Every delivery channel supports two directions — inbound (a requester queries the status of a claim) and outbound (Synapse pushes a GO/NO-GO alert unprompted). A channel adapter is incomplete unless it implements both.
- Escalation Requirement: Every rendered GO/NO-GO alert must state how to escalate — who or what contact point to reach — regardless of channel. Maestro and its channel adapters only ever display this contact information; they never execute an action on the adjudication themselves. **Amended 5 Aug 2026 (Supervisor Override Retirement, below):** originally worded as "a contact point to reach for an override"; override is now retired entirely, so that framing is stale and is corrected here rather than left to mislead a future reader. The contact point now names a resolved authority, not an override path.
- Admin-Override Evidence Principle: An admin override never mutates, replaces, or deletes an existing adjudication record — Core is stateless and re-evaluates from live PostgreSQL/Redis state rather than storing a mutable verdict, so there is no stored decision to flip. An override is validated (`src/supervisor/schemas.py`'s `OverrideRecord`: `extra="forbid"`, mandatory non-empty `justification`), authorized by pure, zero-I/O logic (`src/supervisor/logic.py`'s `evaluate_override`, mirroring `core/rules.py`'s pattern: fails closed if the issuer is unauthenticated, and fails closed if the claim being overridden has no existing adjudication record), and — only if accepted — emitted as its own distinct, SHA-256-signed `OverrideRecord` evidence entry (`evidence/emitter.py`'s `emit_override_evidence`), additive alongside the original `AdjudicationRecord`, linked only by `claim_id`. Core's determinism is preserved: the same claim always adjudicates the same way; an override is a separate, layered, human fact, never a rewritten decision. Exposed live at `POST /supervisor/override` (`src/supervisor/router.py`): 403 if the issuer is unauthenticated, 404 if the claim has no adjudication record on file (unlike `/airlock/claims`, where NO_GO is a valid outcome and always 200 — a rejected *override* means the administrative action didn't happen at all, so it uses real HTTP status semantics instead). Both the original adjudication and the override are now genuinely persisted, append-only, in PostgreSQL — `src/evidence/models.py`/`repository.py` (`adjudication_records`, written by `src/airlock/router.py` right after `emit_evidence()`) and `src/supervisor/models.py`/`repository.py` (`override_records`, written only when an override is accepted, never for rejections). Neither table uses `claim_id` as a primary key: these are audit logs, not latest-state tables, so multiple entries per claim are permitted by design.
- Admin-Override Notification Principle: An accepted override triggers a Maestro alert. Reasoning: an override is exactly the kind of event someone other than the overriding supervisor should hear about — a human just intervened in a fail-closed system, and staying silent about that would undercut the whole point of an audit trail. The alert is built from the existing `OutboundAlert` schema (decision `GO`, a single `rule_trace` entry describing the override, `escalation_contact` naming the overriding issuer) and sent through the existing `WhatsAppAdapter`/`TelegramAdapter` stubs — no new Maestro surface added. This is the *only* place `src/supervisor/` imports `src/maestro/`: `src/supervisor/logic.py`'s `evaluate_override` stays fully decoupled (zero Maestro imports), only `src/supervisor/router.py` (the orchestration layer) wires the two together, mirroring how `src/airlock/router.py` wires Core and Evidence without either depending on the router. This principle covers *override* notifications only.
- NO_GO Notification Principle: **DECIDED 2026-07-31.** A NO_GO adjudication from `POST /airlock/claims` triggers a Maestro alert, for every failure class (`R-PTW-01`, `R-AUTH-01`, `R-ZONE-01`) — not just overrides. GO adjudications deliberately do not trigger one; that asymmetry is intentional, not an oversight. Follows the exact same pattern as the Admin-Override Notification Principle above: `src/airlock/router.py` builds an `OutboundAlert` (via `OutboundAlert.from_evidence_record()`, which now also carries `reason_code` straight from the evidence record — see Reason Code Convention) and hands it to both `WhatsAppAdapter` and `TelegramAdapter` unconditionally, mirroring how `src/supervisor/router.py` is the only place that touches both Core/Evidence and Maestro. `recipient_id`/`escalation_contact` are no longer sourced from `claim.issuer_id`/placeholder text — see Escalation Ownership Principle, below, for the current (2026-07-31, superseding) mechanism. This does not apply to the override flow's `escalation_contact`, which already names the real overriding issuer and remains untouched. Unlike the override endpoint, `/airlock/claims`'s response shape is unchanged — Maestro notification results are not added to the HTTP response; delivery stays a side effect, kept out of the adjudication response contract deliberately, to avoid changing an API shape nothing asked to change.
- Escalation Ownership Principle: **DECIDED 2026-07-31.** Who owns escalating a rejected claim is determined by the adjudicated failure reason (`reason_code`), not by the work activity that was attempted (`claim_type`/`work_type`) — a PTW failure and an authority failure in the same zone are two different people's problem. Resolved deterministically by `src/maestro/directory.py`'s `resolve_authority(zone_id, reason_code) -> AuthorityBinding` (`binding_id`, `role`, `contact_id: Optional[str]`), zero I/O, same discipline as `src/core/rules.py`/`src/supervisor/logic.py`. Precedence, most to least specific: `(zone_id, reason_code)` → `("*", reason_code)` → `("*", "*")`; fails closed (raises) if even the catch-all is missing, rather than returning an unresolved binding. `DIRECTORY_MAP` ships with exactly one entry — the `("*", "*")` catch-all (`BIND-999`, "General Duty Officer", `contact_id=None`) — deliberately: no placeholder names, phone numbers, or fabricated zone/role data are seeded ahead of real site authorities being identified; real `(zone_id, reason_code)` and `("*", reason_code)` entries get added as those are identified (see Open Items). Applies uniformly to GO and NO_GO alike (GO resolves `reason_code=None`, landing on the catch-all) — the Escalation Requirement already applies to every alert regardless of decision. `OutboundAlert.from_evidence_record()` (`src/maestro/schemas.py`) calls `resolve_authority()` itself and populates `recipient_id` (falls back to the binding's `role` when `contact_id` is unset, rather than fabricating a contact), `authority_binding_id`, `assigned_role`, and `escalation_contact` (built from `directory.SUPERVISOR_OVERRIDE_URL`, a fixed system constant, not a per-binding field — deliberately *not* an escalation URL alone this time, since `assigned_role` now separately carries the human-readable "who," resolving the earlier tension that made a bare URL misleading). `src/airlock/router.py` resolves authority a second time, before `emit_evidence()` runs, so `authority_binding_id` can be part of the *signed* evidence record itself (`None` on GO, same pattern as `reason_code`) rather than appended after signing — a deliberate duplicate call to the same pure, deterministic lookup, not a second decision.
- Schema Provisioning Principle: Schema creation is automatic and idempotent, never a manual step. `src/core/init_db.py` runs once per container start (wired into the Dockerfile's `CMD`, before `uvicorn`) and calls `Base.metadata.create_all()` against `src/core/models.py`'s shared `Base.metadata` — the single source of truth for the schema, so there is no second copy of it (e.g. a raw init-SQL script) to drift out of sync. Every module defining a table (`src/core/models.py`, `src/evidence/models.py`, `src/supervisor/models.py`) must be imported inside `init_db.py`, even if none of its classes are referenced directly — SQLAlchemy only registers a table on `Base.metadata` once its model class has actually been imported somewhere, and this was caught as a real bug during live verification (only `authorized_issuers` was created until the other two model modules were explicitly imported). It retries briefly, since `docker-compose`'s `depends_on` only waits for the `db` container's process to start, not for Postgres itself to be ready. `create_all()` (not Alembic) is the deliberate choice for this project's stage: no production data, no schema-evolution history, one developer — Alembic's versioned-migration machinery would add real overhead (autogenerate discipline, upgrade/downgrade scripts in the deploy path) for no current benefit. Revisit this choice once a schema change needs to preserve existing data, or once `create_all()`'s create-only semantics (no `ALTER`s) become limiting. No seed data ships automatically — `scripts/seed_dev_data.py` is a separate, optional, manually-run script for local dev convenience only.
- ePTW Precondition Principle: High-risk work (`ClaimPayload.work_type` in `EXCAVATION`, `LIFTING`, `HOT_WORK`, `CONFINED_SPACE`) may not proceed without a valid, matching Permit-to-Work. This is Rule 0 in `src/core/rules.py`'s `verify_ptw_precondition`, run before Rule 1 (authority) and Rule 2 (zone safety) in `src/core/evaluator.py`'s `adjudicate()` — a high-risk claim with no valid permit is rejected before Core even considers who submitted it or where. `NOMINAL_CIVIL` work bypasses the gate transparently; it is the only category that does. A permit fails the gate closed if it is missing, not `APPROVED`, outside its `valid_from`/`valid_until` window, mismatched on `zone_id`, or mismatched on permit type (`ClaimPayload.work_type` vs `PtwContext.permit_type`, both the same `WorkType` enum — a same-typed comparison, not a string against unvalidated free text). `PtwContext.valid_from`/`valid_until` must be timezone-aware ISO-8601 strings (`src/airlock/schemas.py` rejects naive or unparseable ones at 422, before Core ever has to compare an ambiguous timestamp against "now"). `Verdict` gained a `reason_code` field, added as a new field rather than by introducing a third `decision` value alongside the existing `"GO"`/`"NO_GO"` vocabulary that `emit_evidence()`, `maestro/schemas.py`'s `OutboundAlert`, and every existing test already depend on.
- Reason Code Convention: `Verdict.reason_code` (`src/core/evaluator.py`) uses a rule-ID-style code, `R-<DOMAIN>-<NUMBER>`, one per rule/failure class — not per individual sub-condition within a rule, so every ePTW sub-check (missing permit, wrong status, outside window, zone mismatch, type mismatch) still reports the same `R-PTW-01`. Defined in `src/core/rules.py` alongside the rule functions they describe: `R-PTW-01` (ePTW Precondition Failure, Rule 0); `R-AUTH-01`/`R-AUTH-02`/`R-AUTH-03` (Authority Failure, Rule 1 — see the 2026-08-06 exception below); `R-ZONE-01` (Safety Violation / Zone Safety Failure, Rule 2); `None` on `GO`. `reason_code` is now threaded all the way into `emit_evidence()`'s persisted evidence record (`src/evidence/emitter.py`) — a rejected claim's signed, persisted evidence carries the specific failure reason, not just a generic `decision="NO_GO"` indistinguishable from any other rejection. It remains additive alongside the existing human-readable `reason` string, which is unchanged. **Deliberate exception, 2026-08-06 (`R-AUTH-01` disambiguation):** Rule 1 now produces three codes, not one — `R-AUTH-01` stays the unauthenticated-issuer case (domain-independent, no honest split possible from claim content); `R-AUTH-02`/`R-AUTH-03` split the insufficient-clearance case by the existing `HIGH_RISK_WORK_TYPES` distinction (`src/core/rules.py`'s `classify_authority_failure()`, called by both `check_authority()` and `adjudicate()` — a deliberate duplicate call to one pure function, same pattern as `resolve_authority()`'s two call sites, not two copies of the branching logic). This does not change `RuleOutcome`/`rule_trace`'s wire shape (`rule_id`/`passed`/`reason` only) — `reason_code` stays a `Verdict`-level field, so `src/maestro/schemas.py`'s `RuleConditionResult` (`extra="forbid"`) is untouched.

### Escalation vs. Override — Decoupling Principle (Locked, 5 Aug 2026)
**Partially superseded the same day by Supervisor Override Retirement, below — this section is kept verbatim for history, not edited, per this file's own convention of recording superseding text as a new entry rather than silently rewriting the old one.** At the time this was written, override still existed as a Supervisor-only capability; the "current implementation note" and "override mechanism" language below describe that now-retired state. The underlying instruction it enforced — Frontline Worker escalation must never present as, or lead to, an override/administrative action — still holds and is carried forward by Supervisor Override Retirement, which applies more broadly now that there is no override to conflate escalation with.

Frontline Worker escalation and Supervisor override are separate concepts and must not be conflated in the Frontline Worker UI.

Current implementation note: `escalation_contact` on `OutboundAlert` resolves to the `/supervisor/override` URL. This is correct and unchanged for Maestro's existing WhatsApp/Telegram adapters. However, if/when a Frontline Worker-facing view is built, it must NOT reuse `escalation_contact` as-is, since doing so would silently present "request help" as "request an override" before override scope itself is resolved (see: Supervisor Override Scope Open Item, pending Willy's sign-off).

v0.1 guidance: Frontline Worker screen shows a contact/escalation path only — no override button, no override language, no override URL exposure. `assigned_role` (the "who") may be shown separately from `escalation_contact` (the override mechanism) once this is actually built — they are already structurally separable in the schema, per verification.

### Supervisor Override Retirement (Locked, 5 Aug 2026)
Supervisor override is retired entirely — not scoped down, removed as a capability. This also resolves the Supervisor Override Scope Open Item (verdict-type-unrestricted override): there is no longer an override to scope.

**Replacement mechanism:** a verdict changes only via a new, verifiable claim submitted by the specific licensed/registered authority role that owns the gate being changed, re-adjudicated fresh through Core (`POST /airlock/claims`). This is not an override and not an appeal — it is Core doing exactly what it already always does (stateless, fresh re-adjudication from live state), triggered by the correct authority submitting new facts, not by an administrative action layered on top of an existing verdict.

**Authority set:** PE, QP, PI, PA, PM, SA. Each must be externally verifiable against PEB or MOM registration — **not implemented in this pass; see Open Items.** `PR` (Permit Receiver) is explicitly excluded from this set: it names the executing worker/crew, the same category as the Frontline Worker persona, not an approving/certifying role.

**What actually changed in the repository (2026-08-05):**
- `POST /supervisor/override` (`src/supervisor/router.py`) now returns `410 Gone` unconditionally, before any database access, `evaluate_override()` call, or Maestro notification. A structurally malformed body still 422s at the Pydantic schema boundary first (unrelated to retirement, unchanged fail-closed behavior).
- `evaluate_override()` (`src/supervisor/logic.py`), `OverrideRecord` (`src/supervisor/schemas.py`), `OverrideAuditEntry`/`override_records` (`src/supervisor/models.py`), and `persist_override_record()` (`src/supervisor/repository.py`) are left intact, per instruction — not deleted, simply no longer called from the retired route. Formal removal is a separate future decision, not made here.
- `src/maestro/directory.py`'s `AuthorityBinding` gained an optional `role_type: Optional[AuthorityRoleType]` field (new `AuthorityRoleType` enum: `PE`/`QP`/`PI`/`PA`/`PM`/`SA`). **Schema/structure only** — no real PEB/MOM registration data is populated, and `DIRECTORY_MAP` still ships with only the original untyped `("*", "*")` catch-all (`BIND-999`, "General Duty Officer", `role_type=None`), deliberately retained: removing it before real typed entries exist would fail closed on *every* Maestro alert and the Frontline Worker screen (`GET /frontline/blocked/{claim_id}`), both of which call `resolve_authority()` — a materially larger and different decision than a schema restructuring, not made here.
- `escalation_contact` (`src/maestro/schemas.py`'s `OutboundAlert.from_evidence_record()`) no longer builds a `directory.SUPERVISOR_OVERRIDE_URL` link — pointing an escalation at a retired endpoint would be actively misleading. It now states the resolved authority directly: `f"{binding.role} ({binding.binding_id})"`, e.g. `"General Duty Officer (BIND-999)"`.
- `render_alert_text()` (`src/maestro/formatting.py`) dropped "escalate/**override**" phrasing in favor of plain "escalate" — applies to every alert, GO or NO_GO, on any channel.
- `frontend/blocked-screen/blocked-screen.js` (the Supervisor Blocked Screen) is **untouched** — it still renders an override submission form pointed at `/supervisor/override`. Submitting it now surfaces the 410 retirement message via the component's existing error-handling path (no code change needed there — `formatErrorDetail()` already surfaces a string `detail` verbatim), but the form itself remains visually present. Removing or repurposing that form is a separate, not-yet-made UI decision — flagged here, not resolved.

**Explicitly not decided in this pass** (see Open Items): binding the PE/QP/PI/PA/PM/SA authority set to real PEB/MOM registration data; the specific `reason_code` → role-type routing table (still a working draft); whether/how `ClaimPayload` should carry which authority role is submitting a re-adjudication claim; formal removal of the now-dead override code paths; any change to `frontend/blocked-screen/blocked-screen.js`'s override form.

### Telemetry Transport Security Principle (Locked, 9 Sep 2026)
`POST /telemetry/zone-state` carries no transport-level auth beyond its existing Ed25519 payload signature — this is the locked baseline, not a gap. The signature authenticates *which device* sent a payload; the deployment boundary (client-local infrastructure, never internet-facing — see Two-Track Operational Readiness Model) controls *who can reach the endpoint at all*. A specific client's InfoSec requirements may add a layer (e.g. mTLS) as an additive per-deployment decision — that is not a change to Synapse's baseline design.

### Stage 1 Operational Stories (Locked Classification, 1 Aug — Copilot–Gemini Frontline Worker UI review)
Classifies the frontline-facing interaction stories the Blocked Screen (and any future frontline surface) must represent. Two are current, real behavior, already true of `adjudicate()`/`emit_evidence()` today and test-verified (`tests/test_adjudication.py`, `tests/test_core_eptw.py`); the third is explicitly target-state only.

1. **GO baseline** — valid ePTW, authority verified, zone checks satisfied. Internal `decision`: `GO`. `reason_code`: `None`. Frontline wording: "GO — AUTHORIZED". Render only the actual `rule_trace` data `adjudicate()` returned — no synthesized or assumed passing conditions.
2. **ePTW rejection baseline** — Rule 0 (`verify_ptw_precondition`) fails on an expired permit. Internal `decision`: `NO_GO`. `reason_code`: `R-PTW-01`. Frontline wording: "BLOCKED — PERMIT EXPIRED". Later checks (`authority_check`, `zone_safety_check`) must never be represented as passed — Core short-circuits on Rule 0 failure and never evaluates them at all (`src/core/evaluator.py`'s `adjudicate()`; verified by `tests/test_core_eptw.py::test_adjudicate_rejects_before_authority_check_even_runs`, which asserts `rule_trace` has exactly one entry in this case). Render only evidence actually supplied by Core.
3. **Telemetry or assurance failure** — **TARGET STATE ONLY, NOT IMPLEMENTED.** Requires future constitutional reason codes, evidence schemas, and enforcement behavior that do not exist yet (see Distinct Target-State Assurance Failures, below, and Open Items).

Universal constraint, applying to all three: failure reason codes must never be displayed as, or implied to be, successful rule identifiers. Verified true of the current `blocked-screen.js`/`src/supervisor/router.py` data path as of this writing — `reason_code` and `rule_trace` entries are structurally and visually distinct throughout (`reason_code` renders only in the conflict block via a `.reason-code`-styled span, never inside a `rule-id`-styled, `passed: true` list item) — recorded here as a locked constraint going forward, not a fix to a found violation.

### GO Freshness Principle (Approved in Principle — Copilot/Gemini reviewed, 1 Aug; model resolved in conversation with Willy, 28 Aug 2026 — see below; not yet implemented in code)
"A GO authorizes execution only while its constitutional validity conditions remain satisfied. Expiry, loss of a mandatory authority dependency, or mismatch in its bound execution context terminates that authority immediately. Continued execution requires a newly adjudicated GO. The UI may display authority, but may neither create, extend, nor revoke it independently."

Boundaries: an expired GO ceases authorizing immediately; revalidation may mint a new GO; **Core is the authoritative enforcement boundary** (resolved 28 Aug 2026, below); temporary UI connection loss alone does not revoke a GO; a GO remains bound to its original claim, asset, operator authority, zone, permit context, and relevant state version; the UI must not calculate or invent constitutional authority independently. A countdown may supplement, but never replace, "Authorized now" / "Valid until" / "Last verified" display. Visible UX transitions: GO → "You may proceed"; revalidating → "Wait, verification in progress"; expired or invalidated → "Authorization ended, do not proceed".

**Model resolved 28 Aug 2026 (in conversation with Willy, not repo-derived or Claude-Code-derived): GO validity is context-bound, not time-bound.** A GO remains valid exactly as long as its bound fields — claim, asset, operator authority, zone, permit context, state version, the same list already named in the Boundaries paragraph above — stay unchanged. There is no fixed expiry timer. `valid_until` is derived (invalid the instant any bound field changes), not a stored future timestamp. Core is the authoritative enforcement boundary, consistent with the existing Core-decides/Maestro-delivers architecture (System Principle, top of this file) — Maestro never adjudicates freshness independently, only acts on what Core has already cleared or revoked. This resolves what a GO's validity actually means and who owns enforcing it; it does not resolve how Core detects that a bound field changed after issuance, or what mechanism triggers revocation — those are implementation questions, deliberately out of scope for this documentation-only decision. See Open Items for exactly which of the original six constitutional decisions this does and doesn't close.

**Not implemented.** No freshness/expiry concept exists anywhere in the current adjudication or evidence path today (confirmed by inspection: `evaluated_at` is persisted but not currently used for any freshness check anywhere, and the only expiry concept in the codebase — `PtwContext.valid_from`/`valid_until` — is permit validity, a distinct, already-implemented concern, not GO-verdict freshness). The model above is now resolved; the detection/revocation mechanism, exact signed schema fields, and remaining open items below are not. Do not invent them.

### Two-Track Operational Readiness Model (Locked, 1 Aug)
Synapse's remaining work is formally split into two decoupled tracks, reported separately — never again as a single conflated percentage.

**Track A — Platform Completion:** bounded, lower-risk software/UI work. Frontline GO/BLOCKED experiences, UI consistency, Maestro reason-code presentation, documentation, accessibility, testing, clean demonstration packages.

**Track B — Operational Readiness:** heavyweight real-world deployment work. Site integration, identity/telemetry assurance, real authority directories, system hardening, adversarial testing, deployment procedures, field trials.

Track B is formally ring-fenced: it does not begin until the six open constitutional decisions (GO validity interval, mandatory authority dependencies, signed schema fields, enforcement ownership, future reason codes, assurance-failure evidence schemas — see Open Items' "GO Freshness — unresolved constitutional decisions" entry) are resolved. Resolving those six items is necessary but not sufficient to start Track B — initiation additionally requires Willy's explicit go-ahead. Resolving the six items does not auto-trigger Track B.

**Why this matters, made explicit:** Track B is what the BCA Innovation Sandbox at the Built Environment Innovation Hub targets. The ring-fence exists specifically so Track A UI/demonstration work is never mistaken for Sandbox-ready operational readiness — "Track B remains formally uninitiated pending resolution of the six items" is not just a status label, it is the thing standing between current progress and Sandbox eligibility.

**Excluded scope:** Track B activities — site integration, hardware attestation, live authority linking — must never be smuggled into Track A UI/UX deliverables. Any future handoff touching Track A scope should be checked against this boundary before being accepted as in-scope.

**Reporting language:** no section of `CLAUDE.md` currently states or implies a single completion percentage for Synapse (checked in full, 1 Aug) — there was nothing to retroactively replace. This principle sets the going-forward standard: any future status reporting must report Platform Completion and Operational Readiness as distinct, separately tracked figures, never collapsed back into one number.
